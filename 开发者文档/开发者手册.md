# ULTIMATE_WEB 开发者手册

本文档是当前代码仓库的唯一架构说明。内容以源码、配置和测试为准；当文档与代码冲突时，应先修正文档或确认代码是否已经发生有意变更。

## 1. 项目定位

本项目是个人使用的漫画与视频管理工具，重点是：

- 管理大量本地内容，并保持列表、搜索、筛选和详情页响应稳定。
- 支持预览内容和本地内容两类生命周期。
- 通过统一协议接入可选内容源，不让宿主业务依赖某个具体内容源。
- 支持桌面端、移动端、Linux 和容器化运行。
- 以 JSON 文件作为业务数据源，以 SQLite 索引加速读取；索引可以重建，不能替代业务数据源。

项目不以高并发为目标。设计优先级是数据安全、可恢复、低维护成本、单机大量数据下的可用性。

## 2. 总体架构

```text
浏览器 / 移动 WebView
        |
        | HTTP(S) JSON API、静态资源、媒体资源
        v
Flask 应用入口 comic_backend/app.py
        |
        +-- api/v1                  路由和请求响应转换
        +-- application             用例编排和业务规则
        +-- domain                  实体、仓储接口和领域模型
        +-- protocol                 内容源协议、注册表、Provider 网关
        +-- infrastructure           JSON、SQLite、缓存、任务、日志和文件系统
        +-- core                     路径、运行时、平台和常量
        |
        +-- data/*.json              业务数据源
        +-- data/catalog_index.db    可重建查询索引
        +-- static/                  封面、缩略图和缓存资源
```

前后端通过 `/api/v1` 下的接口通信。前端不直接读取 JSON 或 SQLite；后端也不依赖前端组件的状态结构。媒体文件通过专用静态路由或流式接口提供，列表接口只返回当前分页的数据。

### 2.1 依赖方向

推荐依赖方向如下：

```text
api -> application -> domain
application -> infrastructure
protocol -> 通用协议、基础设施和第三方扩展
core -> 被各层使用的无业务编排基础设施
```

路由层不应承载复杂业务逻辑。业务服务不应拼接 Flask 响应。数据访问应通过仓储或专用基础设施服务完成，避免在多个服务中直接读写同一个 JSON 文件。

## 3. 后端模块设计

### 3.1 应用入口与运行时

| 路径 | 责任 |
| --- | --- |
| `comic_backend/app.py` | 创建 Flask 应用、注册路由、配置鉴权、启动后台组件和提供静态资源 |
| `comic_backend/api/__init__.py` | 注册 API 蓝图 |
| `comic_backend/core/constants.py` | 默认配置、基础目录和全局常量 |
| `comic_backend/core/storage_layout.py` | 普通空间、隐私空间和运行时目录解析 |
| `comic_backend/core/runtime_profile.py` | 识别桌面、移动和容器运行时 |
| `comic_backend/core/config_paths.py` | 配置文件路径解析 |
| `comic_backend/core/ssl_cert.py` | 本地 HTTPS 证书和 SSL 上下文 |
| `comic_backend/core/platform.py` | 宿主平台能力识别，不包含具体内容源特判 |
| `comic_backend/core/host_platform_fallback.py` | 平台能力缺失时的通用回退 |

启动时应先确定数据目录、静态目录、运行时配置和日志目录，再初始化索引、缓存、压缩包能力和协议注册表。移动端后端由应用内运行时启动；桌面端和容器端由各自启动器启动。

### 3.2 API 层

`comic_backend/api/v1/` 按资源和用例分组：

| 模块 | 主要职责 |
| --- | --- |
| `auth.py` | 登录、会话、密码和退出 |
| `comic.py` | 漫画列表、详情、阅读、导入、更新、封面、回收站和内容源调用 |
| `video.py` | 视频列表、详情、导入、缩略图、播放和内容源调用 |
| `recommendation.py` | 预览内容和推荐内容管理 |
| `list.py` | 清单管理和清单内容 |
| `tag.py` | 标签及批量绑定、解绑 |
| `author.py`、`actor.py` | 创作者、演员和订阅相关功能 |
| `history.py` | 阅读和访问记录 |
| `feed.py` | 随机流会话、刷新和分页项目 |
| `sync.py` | 设备配对、清单同步、增量同步和资源传输 |
| `transfer.py` | 局域网文件传输 |
| `teledrive.py` | 远端文件目录和导入流程 |
| `backup.py` | 备份、恢复和备份信息 |
| `config.py` | 系统配置和数据目录变更 |
| `performance.py` | 性能诊断接口 |
| `organize.py` | 数据库整理和文件组织 |
| `ui_state.py` | 用户界面状态 |

路由处理流程应保持为：解析请求 -> 校验参数 -> 调用应用服务 -> 统一转换结果 -> 返回 HTTP 响应。导入、同步、批量删除、封面生成等长任务必须交给任务管理器或后台服务，不应阻塞请求线程。

### 3.3 应用服务层

`comic_backend/application/` 是用例编排层：

- `comic_app_service.py` 和 `video_app_service.py`：内容增删改查、详情、进度、标签和媒体路径。
- `catalog_query_service.py`：列表、搜索、筛选、排序和分页的统一查询入口。
- `content_sorting.py`、`list_query_support.py`：查询参数归一化和排序规则。
- `local_comic_import_service.py`：本地漫画批量扫描、软链接、硬链接、复制和导入提交。
- `local_video_thumbnail_service.py`、`video_runtime_support.py`：视频缩略图和播放运行时能力。
- `comic_online_update.py`：预览内容的检查更新、续载和增量处理。
- `recommendation_app_service.py`：预览库内容和推荐内容的生命周期。
- `cover_thumbnail_service.py`、`cover_versioning.py`：封面版本、缩略图、修复和缓存。
- `tag_app_service.py`、`tag_content_type_guard.py`：标签管理及内容类型约束。
- `list_app_service.py`：清单管理和按清单操作。
- `random_feed_service.py`：随机流策略、会话和懒加载。
- `reading_history_app_service.py`：阅读历史和访问时间。
- `sync_app_service.py`、`sync_directional_service.py`：同步会话、清单范围、资源清单、差异包和应用。
- `lan_transfer_app_service.py`：局域网传输的会话和文件流程。
- `database_organize_service.py`：索引整理、孤立数据和存储清理。
- `persisted_content_metadata.py`：可持久化的内容元数据。
- `storage_usage_service.py`：空间统计和动态目录信息。

应用服务要保持内容类型边界清晰。漫画和视频可以共享分页、标签、封面和任务等基础机制，但不应通过含义模糊的字段互相兼容；公共逻辑应抽象为明确的内容无关服务。

### 3.4 Domain 层与仓储

`comic_backend/domain/` 保存实体、仓储接口和领域边界，当前包含漫画、视频、推荐内容、清单、标签、作者、演员、配置和基础实体。

`comic_backend/infrastructure/persistence/repositories/` 提供 JSON 仓储实现。仓储负责：

1. 读取和写回业务 JSON。
2. 维持实体结构和必要的兼容字段。
3. 在成功写入后通知索引同步机制。
4. 在批量操作中合并提交和索引更新，避免每条记录都重建一次。

`json_storage.py` 提供原子写入、锁定和一致性基础能力。任何业务代码都不应直接使用 `open(..., 'w')` 覆盖主数据文件。

## 4. 数据源与索引

### 4.1 双层存储模型

业务 JSON 是可读、可备份、可迁移的权威数据源。SQLite `catalog_index.db` 是派生索引，保存查询所需的扁平字段和关联表：

- `catalog_item`：内容主记录、标题、作者、演员、评分、时间、路径和原始 `payload_json`。
- `catalog_tag`：内容与标签关系。
- `catalog_list`：内容与清单关系。
- `catalog_author`：内容与作者关系。
- `catalog_index_meta`：各逻辑 JSON 文件的大小、修改时间和索引时间。
- `catalog_index_state`：模式版本和搜索索引状态。
- `catalog_item_search`：可用时的 FTS5 trigram 全文索引。

核心索引代码位于 `comic_backend/infrastructure/persistence/catalog_index/`：

| 文件 | 责任 |
| --- | --- |
| `schema.py` | 表、索引、FTS5 和模式升级 |
| `connection.py` | SQLite 连接、WAL 和连接生命周期 |
| `builder.py` | 从 JSON 构建或增量同步索引 |
| `writer.py` | 单条、批量写入和索引变更提交 |
| `query.py` | 列表、计数、搜索、筛选和分页 |
| `__init__.py` | 对外暴露索引能力 |

### 4.2 查询流程

```text
HTTP 查询参数
  -> catalog_query_service
  -> catalog_index.query
  -> SQL 条件、排序和 LIMIT/OFFSET
  -> 只读取当前页 item_key
  -> 按 key 补充完整 payload
  -> API 返回当前页和总数
```

后端不会为普通列表请求把整个 JSON 库读入内存，也不会把全部结果返回前端。前端只渲染当前页或虚拟列表窗口。详情、阅读器和图片接口按需获取资源。

### 4.3 更新和一致性

- 外部 JSON 变更通过文件元数据检查发现；变更后可以全量重建或进入增量同步路径。
- 应用自身写入时应在同一业务操作中更新 JSON 并提交对应索引变化。
- 批量导入、批量删除、批量标签和整理操作必须使用批处理上下文，在整个批次结束后统一刷新索引。
- 索引损坏或版本不匹配时可以删除 `catalog_index.db` 并从 JSON 重建。
- 索引不可用时才允许走兼容扫描路径；该路径是恢复能力，不是高数据量的主路径。

索引不是第二个数据源。任何只存在于 SQLite、但没有回写 JSON 的业务字段都会在重建后丢失，因此禁止这样设计。

## 5. 媒体、封面和缩略图

### 5.1 路径分层

动态目录由 `core/storage_layout.py` 解析，不能在业务代码中写死绝对路径。普通空间和隐私空间拥有独立的数据、静态、封面和缓存根目录。

常见资源类型：

- 原始漫画页面和视频文件：业务媒体目录。
- 封面：封面目录，按内容标识组织。
- 缩略图：缓存目录，带版本或内容指纹。
- 远端预览缓存：推荐缓存目录。
- 任务日志和诊断：运行时日志目录。

### 5.2 图片请求流程

```text
前端卡片
  -> 图片 URL
  -> 后端检查缩略图是否存在
  -> 存在则直接返回
  -> 不存在则生成或回退到原图
  -> 写入缓存并返回
```

缩略图的作用是降低列表页的磁盘读取、解码和网络传输成本。列表页不应加载原始大图；详情页和阅读器才按需加载更高分辨率内容。封面修复是显式操作，不能在每次列表请求时重复生成。

## 6. 异步任务与批量操作

`infrastructure/task_manager.py` 负责导入、下载、更新、缩略图和其他长任务的状态管理。任务至少需要：唯一 ID、状态、进度、错误信息、开始时间、结束时间和可取消标志。

批量操作必须遵循以下原则：

1. 先收集输入并进行校验。
2. 在批处理上下文中执行文件和 JSON 变更。
3. 每个子项记录可恢复的结果。
4. 批次结束后统一提交索引刷新。
5. 任务失败时保留日志和部分结果，不能把已成功项目回滚为未知状态。

禁止在循环中调用会触发全库索引重建的公共接口。批量删除和批量导入应调用批量仓储或批量索引 API。

## 7. 同步设计

同步分为两类：

- 按清单同步：范围小，适合用户手动选择内容后传输。
- 方向性增量同步：先交换库存和资源清单，再计算差异，最后传输和应用差异包。

同步接口位于 `api/v1/sync.py`，服务位于 `sync_app_service.py` 和 `sync_directional_service.py`。典型流程：

```text
配对 -> 创建会话 -> 获取清单/资源库存
     -> 估算 -> 预览差异 -> 下载差异 -> 应用差异 -> 完成
```

慢网络下，客户端必须使用比普通 API 更宽松的超时策略；服务端应记录阶段耗时、传输字节数、重试次数和失败阶段。大文件不应先完整读入内存，应使用流式响应和临时文件，应用阶段通过校验和确认完整性。

## 8. 前端模块设计

前端位于 `comic_frontend/`，技术栈是 Vue、Vite、Pinia、Axios、Vant、hls.js 和 Playwright。

### 8.1 目录职责

| 路径 | 责任 |
| --- | --- |
| `src/api/` | 按资源封装 HTTP API |
| `src/stores/` | 跨页面状态、缓存和任务状态 |
| `src/views/` | 页面级路由视图 |
| `src/components/` | 可复用展示和交互组件 |
| `src/composables/` | 可复用响应式逻辑 |
| `src/runtime/` | 浏览器、端点、存储和运行时适配 |
| `src/utils/` | 纯函数、格式化、协议和校验工具 |
| `src/layouts/` | 桌面与移动页面布局 |
| `src/router/` | 路由和鉴权导航 |

### 8.2 列表性能规则

- 列表接口始终使用后端分页、排序和筛选。
- 前端只保存当前查询窗口，切换条件时取消或覆盖旧请求。
- 长列表使用分页和虚拟滚动，不一次渲染全部卡片。
- 图片使用缩略图 URL、懒加载和失败占位；不要在卡片中请求原图。
- 详情页、阅读器和播放器按需加载，不与库列表共用大对象。
- Pinia 只保存必要的响应式数据，避免把整库 payload 放入全局状态。

移动端使用底部导航；桌面端可以使用侧边或顶部布局，但业务页面不应依赖某一种导航形态。

## 9. 第三方扩展架构

宿主只认识协议、清单、Provider、能力和配置，不认识任何具体内容源名称。

### 9.1 扩展包结构

```text
example-extension.zip
└── example-extension/
    ├── ultimate-plugin.json
    ├── ultimate_provider.py
    └── private_modules/
```

一个扩展包必须且只能有一个 `ultimate-plugin.json`。清单声明唯一 ID、版本、内容类型、能力、入口、配置、平台支持和依赖。Provider 实现能力调用、参数校验、结果标准化和平台适配。

### 9.2 宿主加载流程

```text
扫描插件根目录
  -> 读取并校验清单
  -> 建立协议注册表
  -> 按 capability 路由到 Provider
  -> 注入配置和运行时上下文
  -> 返回统一结果
```

关键实现：

- `protocol/registry.py`：清单扫描和注册。
- `protocol/base.py`：清单、Provider 和协议基础类型。
- `protocol/provider_manager.py`：Provider 加载、配置和启停约束。
- `protocol/gateway.py`：能力调用网关。
- `protocol/host_service.py`：宿主内容服务。
- `protocol/adapter_api.py`、`metadata_adapter.py`：旧调用路径的边界适配。
- `protocol/extension_service.py`：ZIP/Git 仓库安装、删除、重装、路径安全和依赖池校验。
- `protocol/snapshot_provider.py`：移动端无源码或扩展模式下的协议元数据快照。

宿主不得新增基于具体平台名称的分支。平台差异必须留在扩展清单和 Provider 内部；跨扩展的共同需求应进入协议字段或通用基础设施。

### 9.3 依赖池

`build/resident_dependency_pools.json` 保存平台常驻依赖。打包时合并：

```text
宿主基础依赖 + 常驻依赖池 + 可发现扩展声明依赖
```

扩展安装只安装代码，运行依赖必须已经存在于目标平台依赖池。常驻池不写具体扩展名称；包含原生代码的依赖必须验证 Python 版本、ABI 和目标平台兼容性。版本冲突不能依赖合并顺序解决。

## 10. 打包与运行模式

统一入口：

- `scripts/build_unified.py`：构建多目标 staging 工作区。
- `scripts/package_unified.py`：生成桌面包、Android 工程和依赖池清单。
- `scripts/release_unified.py`：串联构建和打包。
- `build/targets.json`：目标运行时配置。
- `build/packagers.json`：打包器配置。

### 10.1 桌面端

桌面端使用 PyInstaller 生成后端可执行文件，External 模式把扩展代码放入可安装目录，依赖放入通用运行时池；Bundle 模式把已选源码纳入发布包。两种模式共用协议加载和依赖校验。

### 10.2 Android

Android 使用 Capacitor WebView 加内置 Python 运行时。后端监听地址、端口和数据目录由打包配置及运行时环境注入。扩展源码可按模式内置或在应用私有目录安装，应用重启后重新扫描。

Android 依赖池必须使用适配目标 Python 和 ABI 的构件。`build/packagers.json` 中的 Android 配置包括 ABI、Python 版本、归档工具、常驻依赖池和签名配置。

### 10.3 容器

`Dockerfile` 负责前端构建和 Python 运行时镜像，`docker-compose.yml` 负责端口、配置和数据卷。容器内业务数据、配置和媒体路径必须通过卷或环境变量显式提供，不能依赖镜像内临时目录。

## 11. 配置和安全

- `config_templates/` 提供服务端和扩展配置模板。
- 敏感配置只能存储在运行时配置文件或环境变量，API 返回前必须脱敏。
- 扩展安装必须检查 ZIP 路径穿越、清单数量、入口格式、平台声明和依赖池覆盖。
- 局域网同步使用配对令牌和专用请求头，不应绕过鉴权扩大普通会话权限。
- 默认开发配置不等于生产安全配置；发布包应关闭调试并明确监听地址。
- Android 和容器的可写目录必须与只读代码目录分离。

## 12. 测试体系

测试分为四层：

1. `comic_backend/tests/`：后端服务、仓储、索引和基础设施单元测试。
2. `tests/features/**/integration/`：以 HTTP API 和协议契约为中心的集成测试。
3. `tests/features/**/e2e/`：使用 Playwright 验证用户流程和页面交互。
4. `tests/performance/`：索引查询、列表 API 和资源访问的基准测试。

第三方相关测试只验证宿主协议、清单、能力路由、配置、安装和错误契约，不应在宿主测试中写具体扩展名称或真实远端数据。扩展自己的仓库负责 Provider 行为、伪响应、参数和依赖兼容性测试。

推荐命令：

```text
python -m pytest comic_backend/tests -q
python -m pytest tests/features -m integration -q
python tests/tools/run_e2e.py
npm run build --prefix comic_frontend
```

测试数据必须是本地构造的伪数据，不依赖账号、网络、远端站点或真实内容标识。涉及长任务、同步、导入和索引的用例应验证状态转换、幂等性、失败恢复和批量提交次数。

## 13. 新增模块和扩展的规则

新增宿主业务模块时：

1. 先确定领域实体和数据所有权。
2. 为仓储或基础设施定义唯一写入入口。
3. 为列表类功能接入索引查询，不在路由中全量扫描 JSON。
4. 为长任务接入任务管理器和阶段日志。
5. 为批量操作提供批处理边界，禁止循环触发全量刷新。
6. 同时补充单元、集成和必要的 E2E 用例。
7. 更新本手册中对应模块表和流程。

新增扩展时：

1. 独立维护扩展目录和仓库。
2. 编写唯一清单和 Provider。
3. 只实现清单声明的能力，并使用统一输入输出结构。
4. 把平台差异、配置和依赖放在扩展内部。
5. 用伪响应覆盖成功、空结果、错误、重试、部分失败和重复执行。
6. 在扩展自己的 CI 中运行测试，不把远端服务作为门禁前提。

## 14. 变更检查清单

- 是否改变了 JSON 数据源的语义或兼容格式？
- 是否同时更新了索引写入和重建路径？
- 是否把全量读取、全量返回或全量渲染引入了主路径？
- 批量操作是否只在批次结束时刷新索引？
- 是否新增了具体扩展名称或平台特判？
- Android、桌面和容器的可写路径是否仍然有效？
- 是否补充了不依赖网络的回归测试？
- 是否更新了本手册及相关配置说明？
