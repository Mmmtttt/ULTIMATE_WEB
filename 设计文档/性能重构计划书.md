# 性能重构计划书

更新时间：2026-09-01  
适用范围：`ULTIMATE_WEB` 漫画/视频本地库、预览库的加载、显示、搜索、筛选、封面展示性能优化

---

## 1. 背景与目标

当前项目已经支持漫画、视频、本地库、预览库、第三方内容源、清单、标签、回收站、跨端同步等功能。随着数据量增长，用户已经感知到：

1. 本地库和预览库列表加载变慢。
2. 搜索、筛选、排序开始卡顿。
3. 封面显示速度慢，页面可见内容出现明显等待。
4. 当前缺少稳定的性能数据，无法判断主要瓶颈来自后端查询、JSON 解析、前端渲染，还是图片链路。

本次性能重构的核心目标，是在“不改变 JSON 文件作为唯一事实数据源”的前提下，引入可重建的 SQLite 查询索引层，并建立性能测试与回归看护体系。

### 1.1 核心目标

1. 保持 JSON 文件仍是唯一事实数据源，现有数据文件、备份、同步、导入导出能力不被破坏。
2. 通过 SQLite 索引层大幅提升列表加载、搜索、筛选、排序、清单详情、回收站、标签管理候选集查询性能。
3. 通过封面缩略图、版本化 URL、HTTP 长缓存、首屏加载策略提升封面显示速度。
4. 建立可重复运行的性能基准，能够在重构前后量化收益，并在后续开发中防止性能回退。
5. 支持 Windows、Linux、Android、Docker 运行环境。

### 1.2 非目标

第一阶段不做以下事情：

1. 不把 JSON 迁移为主数据库。
2. 不删除现有 JSON 仓储实现。
3. 不重写全部业务服务。
4. 不追求高并发服务端能力。
5. 不把第三方插件或图片代理整体重构。

## 2. 现状判断

### 2.1 后端列表查询瓶颈

当前本地库、预览库的主列表接口虽然已经支持分页参数，但分页发生在后端 Python 内存中。典型流程是：

1. 读取整份 JSON。
2. 反序列化为 Python 对象或字典。
3. 在 Python 列表中筛选、搜索、排序。
4. 对完整结果分页。
5. 序列化当前页响应。

典型位置：

1. 本地漫画列表：`comic_backend/application/comic_app_service.py` 的 `get_comic_list`。
2. 本地视频列表：`comic_backend/application/video_app_service.py` 的 `get_video_list`。
3. 预览漫画列表：`comic_backend/application/recommendation_app_service.py` 的 `get_recommendation_list`。
4. 预览视频列表：`comic_backend/api/v1/video.py` 的 `get_video_recommendation_list`。
5. 通用 JSON 存储：`comic_backend/infrastructure/persistence/json_storage.py` 的 `read` / `atomic_update`。

这类实现对于几百条数据足够简单可靠，但到几千、几万条后，搜索、筛选、排序会稳定变成线性扫描，响应时间会随数据量增长。

### 2.2 前端大集合页面瓶颈

主浏览页 `Library.vue` 和 `Preview.vue` 已经在请求中携带 `paginate/page/page_size`，不是最主要的全量拉取问题。真正容易拖慢的是管理型页面和跨筛选范围操作：

1. 标签管理：`BaseTagManage.vue` 会拉取 home + recommendation 的全量候选内容。
2. 清单详情：`ListDetail.vue` 会拿到完整清单后，在浏览器本地筛选、排序、分页。
3. 回收站：`BaseTrash.vue` 会按 tab 拉完整回收站列表后本地分页。
4. 主库和预览库的“全选当前筛选范围”：会去掉分页参数拉完整筛选范围，再在前端保存选中 ID。

这类页面在桌面端会先表现为等待和卡顿，在 Android 端会更明显地表现为内存压力、滚动掉帧和页面无响应。

### 2.3 封面显示瓶颈

封面慢和列表接口慢是两类问题。

列表接口变快后，如果每页仍然触发大量大图请求，用户仍会觉得“页面没出来”。当前需要重点检查：

1. 封面是否统一有列表专用小图。
2. 本地封面是否使用版本化 URL。
3. HTTP 缓存是否足够长。
4. 首屏可见图片是否被过度 lazy-load。
5. 远程封面是否被直接用于列表页。
6. 同一页面是否有过多并发图片请求。

当前已知线索：

1. Flask `SEND_FILE_MAX_AGE_DEFAULT` 为 300 秒。
2. `/static/cover/<path>` 静态封面路由没有显式长缓存策略。
3. `MediaGrid.vue` 使用 `van-image lazy-load`，需要区分首屏和非首屏。

## 3. 总体方案

### 3.1 架构原则

本次采用“JSON 事实数据源 + SQLite 查询索引 + 可重建读模型”的架构。

```text
JSON files
  comics_database.json
  videos_database.json
  recommendations_database.json
  video_recommendations_database.json
  tags_database.json
  lists_database.json
        |
        | build / refresh / incremental update
        v
SQLite index
  catalog_index.db
        |
        | query/search/filter/sort/page
        v
API response
        |
        v
Frontend list/search/filter pages
```

JSON 仍然负责：

1. 唯一事实数据。
2. 备份恢复。
3. 同步导入导出。
4. 老接口兼容。
5. 详情字段完整保存。

SQLite 只负责：

1. 列表页摘要查询。
2. 搜索。
3. 多条件筛选。
4. 排序分页。
5. 清单/标签/回收站的快速关联查询。
6. 封面摘要与版本查询。

SQLite 文件可以删除重建，不作为唯一数据源。

### 3.2 为什么不只做 JSON 缓存

继续在 JSON 上加内存缓存或索引文件，短期改动更小，但会带来几个问题：

1. 复杂筛选、排序、清单计数、标签关联最终会变成手写查询引擎。
2. 关键词搜索仍然难以高效处理。
3. 缓存失效规则会越来越复杂。
4. 未来新增字段、内容源、筛选条件时维护成本高。
5. Android 和 Docker 场景下，长期占用大内存不稳定。

SQLite 的优势：

1. 单文件，部署简单，Python 标准库内置 `sqlite3`。
2. 适合个人工具的多读少写。
3. 支持索引、排序、分页、聚合、事务。
4. 支持 FTS5 全文搜索。
5. 支持 WAL，提高读写并行能力。
6. 索引库可从 JSON 重建，风险可控。

参考：

1. SQLite WAL：<https://www.sqlite.org/wal.html>
2. SQLite FTS5：<https://www.sqlite.org/fts5.html>
3. SQLite Query Planner：<https://www.sqlite.org/queryplanner.html>

## 4. SQLite 索引层设计

### 4.1 数据库位置

建议放在当前数据目录的元数据目录下：

```text
data/meta_data/catalog_index.db
data/meta_data/catalog_index.db-wal
data/meta_data/catalog_index.db-shm
```

原因：

1. 跟随 `data_dir` 配置。
2. Docker volume 挂载时自然保留。
3. Android 私有目录内也能使用。
4. 不污染项目源码目录。

### 4.2 表结构草案

```sql
CREATE TABLE IF NOT EXISTS content_item (
  item_key TEXT PRIMARY KEY,
  id TEXT NOT NULL,
  media_type TEXT NOT NULL,       -- comic / video
  source TEXT NOT NULL,           -- local / preview
  title TEXT NOT NULL DEFAULT '',
  author_text TEXT NOT NULL DEFAULT '',
  actor_text TEXT NOT NULL DEFAULT '',
  code TEXT NOT NULL DEFAULT '',
  score REAL,
  create_time TEXT NOT NULL DEFAULT '',
  last_read_time TEXT NOT NULL DEFAULT '',
  current_page INTEGER,
  total_page INTEGER,
  is_deleted INTEGER NOT NULL DEFAULT 0,
  cover_path TEXT NOT NULL DEFAULT '',
  cover_path_local TEXT NOT NULL DEFAULT '',
  cover_version TEXT NOT NULL DEFAULT '',
  custom_order INTEGER,
  raw_updated_at TEXT NOT NULL DEFAULT ''
);

CREATE INDEX IF NOT EXISTS idx_content_scope
ON content_item(media_type, source, is_deleted);

CREATE INDEX IF NOT EXISTS idx_content_score
ON content_item(media_type, source, is_deleted, score DESC);

CREATE INDEX IF NOT EXISTS idx_content_create_time
ON content_item(media_type, source, is_deleted, create_time DESC);

CREATE INDEX IF NOT EXISTS idx_content_last_read_time
ON content_item(media_type, source, is_deleted, last_read_time DESC);

CREATE INDEX IF NOT EXISTS idx_content_code
ON content_item(media_type, source, code);
```

```sql
CREATE TABLE IF NOT EXISTS content_tag (
  item_key TEXT NOT NULL,
  tag_id TEXT NOT NULL,
  media_type TEXT NOT NULL,
  PRIMARY KEY(item_key, tag_id)
);

CREATE INDEX IF NOT EXISTS idx_content_tag_lookup
ON content_tag(media_type, tag_id, item_key);
```

```sql
CREATE TABLE IF NOT EXISTS content_list (
  item_key TEXT NOT NULL,
  list_id TEXT NOT NULL,
  media_type TEXT NOT NULL,
  source TEXT NOT NULL,
  PRIMARY KEY(item_key, list_id)
);

CREATE INDEX IF NOT EXISTS idx_content_list_lookup
ON content_list(media_type, source, list_id, item_key);
```

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS content_fts USING fts5(
  item_key UNINDEXED,
  title,
  author_text,
  actor_text,
  code,
  tag_names,
  tokenize = 'unicode61'
);
```

```sql
CREATE TABLE IF NOT EXISTS index_meta (
  source_name TEXT PRIMARY KEY,
  path TEXT NOT NULL,
  size_bytes INTEGER NOT NULL DEFAULT 0,
  mtime_ns INTEGER NOT NULL DEFAULT 0,
  sha256 TEXT NOT NULL DEFAULT '',
  indexed_at TEXT NOT NULL DEFAULT ''
);
```

### 4.3 item_key 规则

`item_key` 用于避免本地库和预览库里同 ID 冲突。

```text
{media_type}:{source}:{id}
```

示例：

```text
comic:local:JM100001
comic:preview:JM100001
video:local:JAVDB900001
video:preview:JAVDB900001
```

### 4.4 查询服务

新增模块建议：

```text
comic_backend/infrastructure/persistence/catalog_index/
  connection.py
  schema.py
  builder.py
  writer.py
  query.py
  consistency.py

comic_backend/application/catalog_query_service.py
comic_backend/application/performance_metrics_service.py
```

职责：

1. `connection.py`：统一 SQLite 连接、WAL、busy_timeout、row_factory。
2. `schema.py`：建表、迁移版本、索引创建。
3. `builder.py`：从 JSON 全量重建索引。
4. `writer.py`：JSON 写成功后的增量索引更新。
5. `query.py`：列表、搜索、筛选、排序、分页查询。
6. `consistency.py`：检测 JSON 和 SQLite 是否一致，必要时标记 stale 或触发重建。
7. `catalog_query_service.py`：给现有 API/service 提供稳定业务接口。
8. `performance_metrics_service.py`：输出埋点和性能快照。

## 5. 一致性设计

### 5.1 一致性级别

目标是一致性可解释、可修复，而不是让 SQLite 成为新的事实数据源。

推荐级别：

1. JSON 写成功是事实提交。
2. SQLite 更新成功则查询立即可见。
3. SQLite 更新失败时，接口可以短暂 fallback 到 JSON 查询，并标记索引 stale。
4. stale 状态下后台重建索引。
5. 重建完成后恢复 SQLite 查询。

### 5.2 启动检测

后端启动时执行：

1. 确保 SQLite schema 存在。
2. 读取 `index_meta`。
3. 对比每个 JSON 文件的 `size_bytes` 和 `mtime_ns`。
4. 如果不一致，触发全量重建。
5. 可配置是否计算 `sha256`。默认只在疑似异常或手动校验时计算，避免启动慢。

### 5.3 增量更新

改造原则：

1. 不在业务层到处手写 SQL。
2. 在 repository 或 application 的写入成功后统一调用 `CatalogIndexWriter`。
3. 批量操作优先一次 JSON atomic_update，再一次 SQLite transaction。

典型写入：

```text
update score/progress/delete/restore/tags/lists/custom_order
  -> JSON atomic_update 成功
  -> CatalogIndexWriter.upsert_item(...)
  -> CatalogIndexWriter.replace_item_tags(...)
  -> CatalogIndexWriter.replace_item_lists(...)
```

批量写入：

```text
batch tag/list/trash/import
  -> JSON atomic_update 一次性修改多条
  -> SQLite transaction 一次性 upsert 多条
```

### 5.4 索引失败处理

索引失败时不要影响主数据写入。

建议行为：

1. 记录错误日志。
2. 写入 `index_health.json` 或 SQLite `index_status` 表，状态设为 `stale`。
3. 列表查询发现 stale 时可选择：
   - 小数据量 fallback JSON 查询。
   - 大数据量返回提示并启动重建。
4. 系统配置页增加“重建性能索引”按钮。

### 5.5 手动重建接口

新增：

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/v1/performance/index/status` | GET | 查看索引状态 |
| `/api/v1/performance/index/rebuild` | POST | 后台重建索引 |
| `/api/v1/performance/index/verify` | POST | 抽样校验 JSON 与 SQLite |

## 6. 封面性能专项

### 6.1 问题拆分

封面慢可能来自：

1. 列表接口返回慢。
2. 图片文件过大。
3. 同页图片请求过多。
4. 浏览器缓存命中率低。
5. 静态资源缓存时间短。
6. 远程封面直连慢。
7. Android WebView 图片解码慢。

因此封面专项必须和接口查询分别测量。

### 6.2 封面索引与小图

新增列表专用封面缓存目录：

```text
data/cache/covers/
  240w/
  360w/
```

或者沿用静态目录：

```text
data/static/cover_thumb/240w/
data/static/cover_thumb/360w/
```

推荐生成规格：

1. 漫画封面：宽 240 或 360，保持比例，优先 WebP，兼容 JPEG。
2. 视频封面：宽 360，保持比例。
3. 列表页默认使用小图。
4. 详情页继续使用原封面或较大图。

SQLite 中记录：

```text
cover_path
cover_thumb_240
cover_thumb_360
cover_version
cover_width
cover_height
cover_size_bytes
cover_source
```

### 6.3 版本化 URL

所有本地封面 URL 增加版本号：

```text
/static/cover_thumb/240w/JM100001.webp?v=1730000000000
```

版本来源：

1. 优先使用文件 `mtime_ns`。
2. 如果业务已有 `local_cover_asset_version`，继续沿用。
3. 远程封面缓存到本地后使用本地版本。

### 6.4 HTTP 缓存

对带版本号的本地封面：

```http
Cache-Control: public, max-age=31536000, immutable
```

对不带版本号的封面：

```http
Cache-Control: public, max-age=300
ETag: ...
Last-Modified: ...
```

这样可以避免封面更新后缓存不刷新，也避免普通浏览时频繁重新请求。

参考：

1. MDN HTTP Caching：<https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching>
2. web.dev lazy loading images：<https://web.dev/articles/browser-level-image-lazy-loading>

### 6.5 前端加载策略

`MediaGrid.vue` 调整为：

1. 首屏前 8-12 张图片使用 eager。
2. 非首屏图片使用 lazy。
3. 切页后预加载下一页前 4-8 张封面。
4. 列表模式不加载封面或加载更小图。
5. Android 端降低每页默认数量或默认小图规格。

## 7. 性能测试体系

### 7.1 测试目标

性能测试要回答四个问题：

1. 当前到底慢在哪里。
2. 重构是否真的变快。
3. 数据量增长后是否仍然可接受。
4. 后续改动是否引入性能回退。

### 7.2 测试分层

```text
tests/performance/
  datasets/              # 固定数据集生成器与数据规格
  benchmark/             # pytest-benchmark 服务层基准
  http/                  # k6 或 Python HTTP 性能脚本
  e2e/                   # Playwright 页面级性能用例
  reports/               # 本地输出，不进入版本库或只保留样例
```

### 7.3 数据集规格

固定种子生成，不使用真实用户数据。

| 档位 | 内容数量 | 标签数量 | 清单数量 | 目标 |
|---|---:|---:|---:|---|
| small | 500 | 50 | 20 | 快速本地调试 |
| medium | 5,000 | 200 | 80 | 日常性能门禁 |
| large | 20,000 | 500 | 200 | 大库主验证 |
| xlarge | 50,000 | 1,000 | 500 | 手动压测 |

每个档位都生成：

1. 本地漫画。
2. 预览漫画。
3. 本地视频。
4. 预览视频。
5. 标签关联。
6. 清单关联。
7. 部分回收站数据。
8. 部分缺失封面、远程封面、本地封面、小图封面。

## 11. 风险与应对

### 11.1 SQLite 与 JSON 不一致

风险：JSON 写成功但 SQLite 更新失败，列表查询看不到最新状态。

应对：

1. JSON 写入成功后再更新 SQLite。
2. SQLite 更新失败标记 stale。
3. stale 时 fallback 或提示重建。
4. 后台自动重建。
5. 增加一致性测试。

### 11.2 Android SQLite/FTS5 支持差异

风险：Android 环境 SQLite 编译能力可能和桌面不同。

应对：

1. 启动时探测 `sqlite3.sqlite_version` 和 FTS5 可用性。
2. FTS5 不可用时降级为普通 LIKE + 索引字段查询。
3. 性能测试至少覆盖 Android 打包环境一次。

### 11.3 索引构建时间过长

风险：首次启动或大库重建耗时。

应对：

1. 后台任务重建。
2. 分批 transaction。
3. 前端显示索引状态。
4. 重建期间允许 fallback JSON。

### 11.4 封面缓存占用磁盘

风险：小封面缓存增加磁盘占用。

应对：

1. 只生成列表规格。
2. 系统配置提供缓存清理。
3. 记录缓存大小。
4. 缺失时按需生成。

### 11.5 SQL 查询语义和旧 Python 语义不一致

风险：排序、筛选、未读、标签组合结果和旧接口不同。

应对：

1. 阶段 0 先建立 JSON baseline 语义测试。
2. SQLite 查询结果必须与 baseline 对比。
3. 对特殊排序字段写明确规则。

5. 带 `?v=` 的封面请求会命中 `Cache-Control: public, max-age=31536000, immutable`。
6. 没有本地封面时保留原远程 `cover_url`，避免预览库封面回退失败。
7. 版本化工具只解析允许的本地媒体目录，并阻止异常相对路径越界探测。

### 17.2 当前效果

这轮优化不改变首屏接口耗时，主要优化重复浏览、切页返回、刷新列表后的封面二次加载速度。

预期收益：

1. 已加载过且文件未变化的封面，浏览器可以直接使用本地缓存。
2. 封面文件变化后，由于 `mtime_ns` 改变，URL 自动变化，不会出现旧封面缓存不刷新的问题。
3. 原始 `cover_path` 不变，详情页、同步、导入导出等旧逻辑风险较低。

### 19.1 已落地

7. 实测发现“搜索 + 标签/作者/清单强筛选”场景中，旧 LIKE 在候选集很小时更快，因此采用混合策略：强筛选组合继续走 LIKE，纯关键词且每个词不少于 3 字符时才走 FTS。

阶段性结论：FTS5 trigram 已可作为安全的纯关键词加速路径，但本轮在现有数据模型下收益有限，不是当前最大的性能收益来源。真正明显的体感优化仍主要来自 SQLite 分页/排序筛选索引、增量同步、封面长缓存和列表缩略图。
