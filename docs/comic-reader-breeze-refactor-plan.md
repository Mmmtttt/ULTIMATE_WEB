# 漫画阅读器重构计划书

## 1. 文档目的

本计划用于将 ULTIMATE_WEB 的漫画阅读体验系统性提升到 Breeze 阅读器的能力水平，同时保留当前项目的 Web、Windows、Linux、Android、Docker 部署方式，以及本项目已有的本地漫画、预览漫画、软引用、第三方来源和章节数据能力。

本文件同时作为实施跟踪与验收基线；方案确定后，代码改动和测试结果持续回填到本文档。

## 2. 约束与不可变原则

1. 本地库和预览库必须尽量共用同一个阅读器内核。
2. 本地库与预览库的差异只能存在于数据源适配、缓存状态、下载能力和访问权限，不允许各自复制一套翻页、缩放、预加载逻辑。
3. 漫画详情页章节功能继续保留；阅读页默认不展示章节列表，遵守现有产品约束。
4. 阅读进度、阅读记录、路由返回和章节跳转不能因重构丢失。
5. 不要求一次性重写全部功能，必须按阶段提交、可单独验证、可回退。
6. 所有高耗时操作必须可取消，离开阅读页后不得继续无界加载。
7. 桌面端和手机端使用同一套业务模型，交互层允许根据输入设备做细节适配。
8. 不引入只适用于桌面浏览器或只适用于 Android 的核心逻辑。

## 4. Breeze 功能与设计借鉴

### 4.1 渲染模式

Breeze 的纵向模式使用 `ListView.builder`，横向模式使用 `PageView.custom` 和 `SliverChildBuilderDelegate`：

- [column_mode.dart](D:/code/Breeze/lib/page/comic_read/widgets/modes/column_mode.dart:113)
- [row_mode.dart](D:/code/Breeze/lib/page/comic_read/widgets/modes/row_mode.dart:159)

它们只构建视口附近的页面，不会让漫画总页数直接等比例转化为 Widget 数量。这是最值得借鉴的核心。

### 4.2 图片缓存

Breeze 的图片流程是缓存优先：已下载资源、应用缓存、网络资源依次检查；真正显示的图片使用本地文件。预加载只负责把有限数量的图片写入缓存，不负责创建整个阅读布局：

- [reader_image_prefetch_controller.dart](D:/code/Breeze/lib/page/comic_read/controller/reader_image_prefetch_controller.dart:13)

本项目不能直接复制本地文件缓存，因为浏览器客户端可能是局域网内另一台设备。应借鉴缓存优先原则，具体实现采用浏览器 HTTP 缓存、预览缓存目录和可选的 Cache API。

### 4.3 图片尺寸和长页面布局

Breeze 使用 `ImageSizeCubit` 和 `ImageSizeCacheStore` 保存图片宽高，用于估算纵向布局和深页跳转：

- [image_size_cubit.dart](D:/code/Breeze/lib/page/comic_read/cubit/image_size_cubit.dart:27)

本项目当前主要依赖浏览器完成图片加载后再测量 DOM，未加载图片时只能使用估算位置。应借鉴其“尺寸是页面元数据”的设计。

### 4.4 章节和连续阅读

Breeze 使用 `ReaderSeamlessCubit` 管理已加载章节、全局槽位、章节边界和邻章预取：

- [reader_seamless_cubit.dart](D:/code/Breeze/lib/page/comic_read/cubit/reader_seamless_cubit.dart:44)
- [ARCHITECTURE.md](D:/code/Breeze/lib/page/comic_read/ARCHITECTURE.md:87)

本项目应借鉴“章节映射和加载状态只有一个真相源”，但不复制 Breeze 阅读页中可见的章节过渡卡片，因为现有需求明确要求阅读页不体现章节。章节只在详情页显示，阅读器内部保留章节到页码的映射即可。

### 4.5 状态和副作用分层

Breeze 将阅读器拆分为轻量状态、章节状态、输入控制器、动作控制器、历史控制器、系统栏控制器、音量控制器、自动阅读控制器和生命周期控制器。其职责约定见：

- [ARCHITECTURE.md](D:/code/Breeze/lib/page/comic_read/ARCHITECTURE.md:78)

需要借鉴的是职责边界，不是文件数量。Breeze 自己也承认 `ReaderSeamlessCubit` 过大、State 编排仍然偏重、部分类型较动态，因此不建议照搬其全部目录。

## 6. 本地库与预览库的统一边界

### 6.1 统一阅读内核

建议新增一个与页面无关的阅读域模型和控制层，至少包含：

- `ReaderSession`：一次阅读会话的生命周期、会话 token 和销毁状态。
- `ReaderPage`：页码、稳定 key、图片地址、尺寸、章节信息和可用状态。
- `ReaderViewport`：当前模式、视口尺寸、当前页和滚动位置。
- `ReaderLoadWindow`：当前页附近允许加载的页面范围。
- `ReaderLoadQueue`：有限并发、优先级、去重、取消和失败重试。
- `ReaderNavigation`：上一页、下一页、滑块跳转、章节起始页和边界行为。
- `ReaderZoomController`：缩放、锚点、平移、惯性和重置。
- `ReaderHistoryController`：进度写入、恢复和退出前刷新。
- `ReaderSettings`：阅读模式、方向、单页/双页、背景、自动阅读和预加载设置。

### 6.2 来源适配器

本地库和预览库分别实现轻量数据适配器，例如：

- `LocalComicReaderSource`：本地文件列表、软引用密码、TeleDrive、本地缓存状态。
- `PreviewComicReaderSource`：预览页面、已缓存页面、下载任务和远程页面地址。

适配器只提供统一接口，不参与翻页、缩放和工具栏 UI。阅读内核只知道“页面是否可用、如何获取页面、是否需要权限”，不知道页面来自哪个库。

### 6.3 页面组件

建议拆为：

- `ComicReaderShell`：路由接入、来源适配和生命周期接线。
- `ReaderCanvas`：负责上下/左右两种渲染模式。
- `ReaderChrome`：顶部栏、底部栏、进度和操作菜单。
- `ReaderSettingsPanel`：阅读设置。
- `ReaderPageItem`：单页图片、占位、失败和重试。
- `ReaderGestureLayer`：鼠标、触摸、键盘和滚轮输入。

两条路由只负责创建不同的 SourceAdapter，不再各自维护一套完整阅读器。

## 7. 分阶段实施计划

### 阶段 0：基线和行为锁定

目标是先冻结当前功能，避免后续优化过程中出现“性能变好了但翻页行为变了”。

工作内容：

1. 建立本地库和预览库的阅读行为测试数据。
2. 固定至少 10 页、100 页、1000 页和多章节漫画样本。
3. 记录当前模式切换、页码、进度、返回、缩放和章节跳转行为。
4. 统一定义页码是 1-based，内部 slot 是否 0-based。
5. 明确第三方页面、软引用、预览未缓存页面的失败状态。

验收：现有核心测试在未重构代码上通过，并保存性能基线，包括首屏时间、首次可翻页时间、内存和网络请求数量。

### 阶段 1：修复加载窗口和退出取消

这是收益最高、风险最低的阶段，优先于任何视觉重构。

工作内容：

1. 恢复普通状态的有限窗口，默认前 20 页、后 60 页。
2. 恢复定位阶段使用更小窗口，定位完成后切换到普通窗口。
3. 队列只能接受窗口内页面，不能再使用包含全部页码的序列。
4. 页面向前滚动时取消窗口外未完成任务。
5. 每次重新加载创建新的 session token，旧请求不能回写。
6. 退出阅读页、切换漫画和重试时取消活动图片请求。
7. 第三方图片 URL 也必须遵守相同窗口。
8. 本地库和预览库阅读器同时接入，不能只修 `ComicReader.vue`。

验收：1000 页漫画在普通状态不会产生窗口外请求；离开阅读页后不再出现新增图片请求；切换漫画后旧请求不会修改新页面。

### 阶段 2：统一阅读会话和状态模型

工作内容：

1. 抽取共享 `useComicReaderSession` 或等价的阅读控制层。
2. 明确组件状态、阅读状态、来源状态和临时手势状态的边界。
3. 将 `ComicReader.vue` 和 `RecommendationReader.vue` 的重复逻辑迁移到共享层。
4. 决定 [reader.js](D:/code/临时并行开发目录/ULTIMATE_WEB/comic_frontend/src/stores/reader.js) 是迁移为唯一真相源，还是删除其未使用部分；禁止长期保留两套状态。
5. 将进度保存、恢复和路由返回统一化。

验收：本地库和预览库通过相同的阅读内核测试；任一模式的缩放、翻页、退出取消和进度保存不需要写两份测试逻辑。

### 阶段 3：统一显示模式和输入系统

工作内容：

1. 建立 `ReaderMode` 枚举：`column`、`row`、`singlePage`、`doublePage`。
2. 建立 `ReadingDirection`：`ltr`、`rtl`。
3. 单页、双页和方向设置使用统一模型，不通过多个布尔值交叉推断。
4. 统一上一页、下一页、点击区域、触摸滑动和键盘动作。
5. 缩放状态下禁止误触发翻页。
6. 桌面端保留鼠标拖拽、右键/滚轮等合理输入；手机端保留单指翻页和双指缩放。
7. 对触摸屏笔记本使用输入能力检测，而不是简单用 User-Agent 分支。
8. 统一工具栏自动隐藏、点击唤出、全屏和移动端安全区域处理。

验收：电脑、普通手机、全面屏手机、触摸屏电脑分别执行相同的模式和输入测试。

### 阶段 4：图片尺寸元数据和稳定定位

工作内容：

1. 将图片列表升级为页面清单，每页包含稳定 key 和尺寸字段。
2. 本地漫画首次读取时获取图片尺寸，之后缓存到后端或浏览器可用缓存。
3. 预览漫画使用已知尺寸；未知尺寸使用安全比例占位。
4. 纵向布局先使用估算高度，真实图片加载后再做局部校准。
5. 深页跳转采用“粗略偏移 + 页面出现后的精确校准”。
6. 图片尺寸缓存 key 必须包含内容 ID、章节或页面路径，避免内容替换后串尺寸。

验收：重新进入长漫画时，恢复页码不因前面图片尚未加载而大幅跳动；切换章节、方向和窗口大小后仍能定位到正确页。

### 阶段 5：有限页面虚拟化

先做横向模式，再做纵向模式。

工作内容：

1. 横向模式只保留当前页附近的有限 slot，并维护前后占位尺寸。
2. 纵向模式先实现固定估算高度的窗口化页面容器。
3. 页面进入窗口时挂载图片组件，离开窗口时卸载图片组件，但保留轻量占位。
4. 不在 DOM 中保留几千个完整图片组件。
5. 图片真实尺寸变化时，只修正受影响的滚动偏移，不重置当前页。
6. 在虚拟化稳定后再决定是否引入第三方虚拟列表库；不得为了引入库而改变部署兼容性。

验收：1000 页漫画的 DOM 数量和内存占用接近固定范围，而不是随总页数线性增长；上下滚动、深页跳转、返回恢复均不丢页。

### 阶段 6：自动阅读、精细交互和平台能力

工作内容：

1. 增加条漫自动阅读。
2. 增加单页自动翻页。
3. 增加自动阅读速度、距离、间隔、暂停按钮显示等设置。
4. 用户手动滚动或翻页时，自动阅读让位并按规则暂停或重新计时。
5. 增加单页/双页切换时的当前页保持。
6. 增加滚轮、键盘、触摸和音量键的动作映射层。
7. 为 Android 预留系统栏、音量键和横竖屏适配接口，Web 端没有能力时安全降级。
8. 完善图片单页重试、跳过、重新加载和错误说明。

验收：自动阅读不与手动操作争抢；页面销毁后定时器、动画、事件监听和请求全部结束。

### 阶段 7：清理和长期维护

工作内容：

1. 删除重复的阅读状态和重复事件处理。
2. 将纯计算逻辑移到可单测的模块。
3. 将本地库和预览库的差异集中在适配器目录。
4. 为阅读内核补充维护文档和状态真相源说明。
5. 记录预加载窗口、缓存上限和虚拟化策略，禁止后续修改无意恢复全量加载。

## 8. 缓存和资源策略

### 本地库

- 本地图片由后端文件接口提供。
- 优先使用浏览器 HTTP 缓存。
- 服务器端继续使用路径列表缓存，但后续可增加页面尺寸索引。
- 不把所有图片复制到额外缓存目录，避免存储翻倍。
- 软连接只读取真实目标，删除和清理逻辑不能触碰真实文件。

### 预览库

- 已缓存页面优先读取本地缓存。
- 未缓存页面按当前窗口请求。
- 预览下载任务与阅读预加载必须区分，不能因为阅读而触发整部漫画下载。
- 浏览器端只能展示当前可取得的页面状态，不把“远端存在”误认为“本地已缓存”。

### 通用规则

- 预加载只是体验优化，不得影响首屏可读。
- 预加载请求必须有最大数量、最大并发和取消入口。
- 缓存 key 必须包含来源、内容 ID、章节 ID 和页面路径。
- 图片 404、密码错误、网络错误和服务器错误要分别处理。

## 10. 风险和取舍

### 直接照搬 Breeze 的风险

1. Flutter 的 `ListView` 和 `PageView` 不能直接转换为浏览器 DOM 方案。
2. Breeze 的本地文件缓存不适合局域网远程浏览器客户端。
3. Breeze 的 `ReaderSeamlessCubit` 本身已经很大，直接模仿会把复杂度搬到 Vue。
4. 章节无缝加载、尺寸估算和滚动校准组合后，容易出现页码和滚动位置不同步。
5. 完整虚拟化会影响现有 CSS、缩放、双击、触摸和章节跳转，必须后置实施。

### 推荐的取舍

优先保证阅读稳定性和可取消加载，再追求完整虚拟化。第一阶段不改变用户看到的阅读界面，只修复窗口、队列和生命周期。随后统一内核，再引入尺寸缓存和虚拟化。
